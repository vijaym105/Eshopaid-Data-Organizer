# eShopaid Data Collector

An automated API integration and data processing application built with Java and Spring Boot to retrieve, process, and organize transaction data from the eShopaid REST API.

The application uses a separate authentication service to obtain access tokens and a data processor to fetch transaction records through multiple API methods. Responses are processed and stored as individual JSON files in a structured directory hierarchy.

## Overview

The project automates the extraction of purchase and sales-related data from eShopaid APIs.

It consists of two independent Java applications:

1. **API Authentication**: Authenticates with the eShopaid API and stores the access token in a JSON file.
2. **Data Processor**: Reads the stored token, calls the required API methods, processes responses, and saves transaction records as JSON files.

Both applications are designed to run as standalone JAR files and can be scheduled using Windows Task Scheduler.

## Features

- Automated API authentication and token management.
- Integration with multiple eShopaid API methods.
- HTTP request handling using Spring's REST client.
- JSON response parsing and transaction extraction.
- Separate output directories for individual API methods.
- Individual JSON files for transaction records.
- Automatic directory creation.
- Logging for execution status, API responses, and processing errors.
- Error handling that allows subsequent API requests to continue when one request fails.
- Scheduled execution using Windows Task Scheduler.
- Configurable API endpoints, token paths, and output directories.

## Technology Stack

- **Language:** Java
- **Framework:** Spring Boot
- **Build Tool:** Maven
- **API Communication:** REST / HTTP
- **JSON Processing:** Jackson
- **Logging:** SLF4J with Spring Boot logging
- **Automation:** Windows Task Scheduler

The applications are configured to target Java 17 for deployment compatibility.

## Architecture

The project follows a two-application architecture.

```text

              |                     |
              v                     ^
      API Authentication       Data Processor
              |                     |
```

## API Methods

The Data Processor currently handles the following service methods:

| Service Method | Purpose |
|---|---|
| `PullPurchaseReturn` | Retrieves purchase return data |
| `PullSalesReturn` | Retrieves sales return data |
| `PullSales` | Retrieves sales data |
| `PullPurchase` | Retrieves purchase data |

The actual data returned depends on API availability, request parameters, and the data available for the requested date.

## Processing Workflow

### 1. Authentication

The authentication application sends a request to the eShopaid token endpoint using the required credentials and service method.

When authentication succeeds, the returned access token is stored in a JSON file.

Example token file structure:

```json
{
  "token": "REDACTED_ACCESS_TOKEN",
  "generatedAt": "2026-10-19T10:30:00"
}
```

The example above is illustrative. Never commit real access tokens or credentials to version control.

### 2. API Requests

The Data Processor reads the token from the configured token file and sends authenticated requests to the eShopaid `ProcessData` endpoint.

Requests include the relevant service method, date range, page number, and authentication token.

### 3. JSON Processing

The application parses the API response and checks the result status.

For successful responses, it extracts the transaction records from the relevant JSON structure.

Responses indicating that no data is available are handled separately from technical errors.

### 4. File Generation

Each extracted transaction is written to an individual JSON file inside the directory corresponding to its API method.

Example:

```text
Processed-Data/
├── PullPurchaseReturn/
│   ├── PullPurchaseReturn-1_...json
│   └── PullPurchaseReturn-2_...json
├── PullSales/
│   ├── PullSales-1_...json
│   └── PullSales-2_...json
├── PullSalesReturn/
└── PullPurchase/
```

File names include the service method, record sequence, available transaction identifier, and execution timestamp.

### 5. Scheduled Execution

Windows Task Scheduler can execute the applications automatically.

The intended schedule is:

- **API Authentication:** Every 30 minutes.
- **Data Processor:** Every 3 hours.

The authentication task should run before the processor task when their schedules overlap, allowing the processor to use a recently generated token.

## Configuration

Application settings are stored in each application's `application.properties` file.

### API Authentication

Configure the authentication endpoint and token destination.

Example:

```properties
spring.application.name=api-authentication

auth.api.url=https://your-eshopaid-host/eShopaidRestService/eShopaidService.svc/Token
auth.service-method=GetToken

auth.username=${AUTH_USERNAME}
auth.password=${AUTH_PASSWORD}

auth.token-file=E:/Data Collector/API-Authentication/token/token.json

spring.main.web-application-type=none
```

### Data Processor

Configure the processing endpoint, token file, and output directory.

```properties
spring.application.name=data-processor

purchase.return.api.url=https://your-eshopaid-host/eShopaidRestService/eShopaidService.svc/ProcessData

purchase.return.token.file=E:/Data Collector/API-Authentication/token/token.json

processor.output.directory=E:/Data Collector/Processed-Data

spring.main.web-application-type=none
```

Replace the example API host with the actual endpoint supplied by the API provider.

Update the directory paths to match the target machine.

**Important:** The configuration examples use `E:` as the deployment drive. Verify that the drive exists on the target machine before execution.

## Environment Variables

Credentials should be supplied through environment variables or an approved secret-management mechanism.

For a PowerShell session:

```powershell
$env:AUTH_USERNAME = "YOUR_USERNAME"
$env:AUTH_PASSWORD = "YOUR_PASSWORD"
```

Run the authentication application from the same session.

These variables are temporary and apply only to the current process environment. For scheduled execution, configure the variables securely for the Windows account that runs the scheduled task.

Do not store actual passwords, access tokens, or other secrets in the repository.

## Build from Source

Clone the repository:

```bash
git clone https://github.com/YOUR_USERNAME/eshopaid-data-collector.git
```

Navigate to the authentication project:

```powershell
cd API-Authentication
```

Build the authentication application:

```powershell
.\mvnw.cmd clean package -DskipTests
```

Repeat the build process inside the Data Processor project:

```powershell
cd ..\Data-Processor
.\mvnw.cmd clean package -DskipTests
```

The generated executable JAR files will be located in their respective `target` directories.

Ensure that the final artifacts are built and tested against the Java version required by the deployment environment.

## Running the Applications

### Start API Authentication

Set the required environment variables, then execute:

```powershell
java -jar ".\api-authentication-1.0.0.jar"
```

Verify that authentication succeeds and the token file is created at the configured location.

### Start Data Processor

Execute the processor after the token file has been generated:

```powershell
java -jar ".\data-processor-1.0.0.jar"
```

Verify the application logs and confirm that successful API responses produce the expected JSON files.

The paths above assume that the commands are executed from the appropriate application directories.

## Windows Task Scheduler

The applications can be configured as separate scheduled tasks.

### Authentication Task

- Program: `java`
- Arguments: `-jar "E:\Data Collector\API-Authentication\api-authentication-1.0.0.jar"`
- Start in: `E:\Data Collector\API-Authentication`
- Schedule: Every 30 minutes

### Data Processor Task

- Program: `java`
- Arguments: `-jar "E:\Data Collector\Data-Processor\data-processor-1.0.0.jar"`
- Start in: `E:\Data Collector\Data-Processor`
- Schedule: Every 3 hours

Configure both tasks to run under an account with the necessary directory and network permissions.

For production use, configure appropriate failure handling, execution history, and a policy that prevents overlapping instances.

## Error Handling and Logging

The applications log execution details to help diagnose failures.

The Data Processor records information such as:

- API method being processed.
- HTTP response status.
- Response size.
- API result status.
- Number of transaction records found.
- File creation results.
- Processing failures.

If one API call fails, the processor attempts to continue with the remaining methods.

A successful HTTP response does not necessarily mean the API operation succeeded. The application must also inspect the result returned in the JSON payload.

## Security Considerations

- Never commit API credentials, passwords, or access tokens.
- Keep production configuration and secrets outside public source control.
- Restrict access to token and log files.
- Avoid logging sensitive request headers or complete authentication responses.
- Use HTTPS for API communication.
- Rotate any credentials or tokens that have been exposed.
- Review generated business data before sharing logs or sample output files.

## Current Limitations

- The processor currently requests page 1 from each API method.
- Complete multi-page retrieval requires additional pagination handling.
- The available response structure may differ between API methods.
- API failures and empty results depend on the upstream service response.
- The target machine must have the required network access, Java runtime, credentials, and filesystem permissions.
